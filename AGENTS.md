# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Commands

```bash
# Run all tests
bun test --conditions=padrone@dev

# Run a single test file
bun test --conditions=padrone@dev packages/padrone/tests/parse.test.ts

# Type check (uses tsgo / native TypeScript preview)
bun run typecheck

# Lint
bun run lint

# Format
bun run format

# Lint + format + fix
bun run fix

# All checks (lint + test + typecheck)
bun run checks

# Build the padrone package
cd packages/padrone && bun run build

# Run the padrone CLI in dev mode
bun --filter=padrone start
```

The `--conditions=padrone@dev` flag is critical — it resolves package exports to source `.ts` files instead of built `.mjs` files, enabling direct TypeScript execution in tests and dev.

## Project Structure

Monorepo with bun workspaces: `packages/*`, `examples/*`, `docs/`. The homepage terminal (`docs/src/components/terminal/`) runs `examples/pizza-example` in the browser through a custom `PadroneRuntime` (ghostty-web terminal, a small shell, `padroneConfig({ loadConfig })` over an in-memory file system, completion via `__complete`); keep that example working in both Bun and the browser.

The core library lives in `packages/padrone/`:
- `src/types.ts` — All type definitions (`PadroneCommand`, `PadroneBuilder`, `PadroneProgram`, interceptors, extensions, etc.). PadroneCommand has 8 generic type params.
- `src/create.ts` — `createPadrone()` factory and builder object. Wires together the modules below. Immutable builder methods (configure, arguments, action, command, mount, intercept, extend, etc.).
- `src/exec.ts` — Core execution pipeline: parse → validate → execute phases. Contains `execCommand()`, `collectInterceptors()`. Signal handling and error help display are handled by extensions.
- `src/validate.ts` — CLI input parsing (`parseCommand`), argument preprocessing (`buildCommandArgs`), schema validation (`validateCommandArgs`), unknown arg detection, stdin reading.
- `src/program-methods.ts` — Program API methods: `cli()`, `eval()`, `run()`, `parse()`, `tool()`, `stringify()`, `help()`, `api()`, `repl()`, `mcp()`, `serve()`, `completion()`.
- `src/suggestions.ts` — "Did you mean?" formatting (`formatSuggestions`), issue enrichment with fuzzy suggestions.
- `src/command-utils.ts` — Interceptor chain execution (`runInterceptorChain`, `wrapWithLifecycle`), command tree utilities, sync/async preservation helpers (`thenMaybe`).
- `src/parse.ts` — CLI input tokenizer/parser. Handles flag stacking, `--key=value`, `--no-*` negation, positional args, nested keys.
- `src/args.ts` — Schema metadata extraction (`extractSchemaMetadata`), option preprocessing (flags/aliases/negatives), positional config parsing, coercion.
- `src/type-utils.ts` — Advanced type utilities (`MaybePromise`, `PickCommandByName`, `IsGeneric`, `OrAsync`, etc.).
- `src/type-helpers.ts` — User-facing inference helpers (`InferArgsInput`, `InferArgsOutput`, `InferCommand`, `InferContext`).
- `src/mcp.ts` — *(experimental)* Model Context Protocol server (2025-11-25 spec). Streamable HTTP and stdio transports.
- `src/serve.ts` — *(experimental)* REST HTTP server. Exposes commands as endpoints with OpenAPI docs (Scalar).
- `src/help.ts` / `src/formatter.ts` — Help generation in multiple formats (text, ansi, markdown, html, json).
- `src/interactive.ts` — Auto-prompting for missing fields using enquirer.
- `src/wrap.ts` — *(experimental)* Wrapping external CLI tools.
- `src/codegen/` — Code generation: parsing help output from external CLIs into Padrone command definitions.
- `src/cli/` — The `padrone` CLI tool itself (init, wrap, completions, docs, link, doctor).
- `src/test.ts` — Test utilities exported as `padrone/test`.

## Key Conventions

- **Zod v4**: Always import as `import * as z from 'zod/v4'` — never bare `zod` or `zod/v3`. Enforced by biome lint rule.
- **Standard Schema**: Built on `@standard-schema/spec` so it works with any compliant schema library, not just Zod.
- **Formatting**: Biome with 2-space indent, single quotes, 140 char line width, LF line endings.
- **Imports**: Use `.ts` extensions in source imports (`verbatimModuleSyntax` is enabled).
- **Builder terminology**: The method is `.arguments()` (not `.options()`). Action handler param is `args` (not `options`).
- **Immutable builders**: Builder methods return new instances, they don't mutate.

## Changelogs

Releases are managed by [Tegami](https://tegami.fuma-nama.dev) (config in `scripts/tegami.mts`). When asked to commit with a changelog entry, run `bun run tegami` or add a `.tegami/*.md` file directly. Each entry has `packages:` frontmatter (the package and bump type) and a body with at least one `#`/`##`/`###` heading:

```md
---
packages:
  padrone: patch
---

## Short summary of the change
```

Keep entries concise — short sentences covering only user-facing changes, no implementation details. All packages share one version via the `all` group (`syncBump`), so the bump applies across the workspace; only `padrone` is published (the rest are private).

## Architecture Notes

**Async tracking**: `TAsync` generic param tracks whether a command uses async validation. `asyncSchema()` brands a schema with `'~async': true`. `MaybePromise<T, TAsync>` conditionally wraps return types. Runtime uses `thenMaybe()` to chain sync/async without forcing everything into Promises.

**Interceptor system**: Onion model with 7 phases: start → parse → route → validate → execute → (error) → shutdown. `collectInterceptors()` in `exec.ts` walks the parent chain (root outermost, subcommand innermost). Start/parse use root interceptors only. Route/validate/execute use the full collected chain (root + command). Error/shutdown run in two layers: command-level interceptors first (for validate/execute failures), then root-level interceptors (for all failures including parse); a failed command's shutdown is deferred (`deferredShutdowns` in `core/interceptors.ts`, keyed by the run's pipeline state) until the root error handlers have run, so it reports after the printed error; if it throws, the root's shutdown still runs and the error is rethrown after. All interceptor phase contexts include `caller` (the invocation method: 'cli', 'eval', 'run', etc.) and `signal` (AbortSignal for cancellation). `defineInterceptor(meta, factory)` is the recommended API — the factory is called fresh per execution, enabling cross-phase state sharing via closures. Supports `.provides<T>()` and `.requires<T>()` for typed context (type-level only). Interceptors with the same `id` are deduplicated (last wins), across layers too: `execCommand` passes the root interceptors a command-level one overrides to `wrapWithLifecycle` as `overridden`, so they skip the root error/shutdown layer. Builder calls re-parent built subtrees deeply (`withParent` in `create.ts`), so `getRootCommand`/events from a mounted program's subcommands reach the new root. `.on()`/`.requires()` on a `defineInterceptor` value return a new interceptor (`buildInterceptorFn` wraps the factory in a fresh function), never mutating a shared one. Meta `callers` (e.g. `LOCAL_CALLERS`/`REMOTE_CALLERS` from `core/interceptors.ts`) skips an interceptor for other callers in `runInterceptorChain`, like `disabled`, but it still counts as registered for `requires`. Custom events (`src/core/events.ts`): `defineEvent<T>(id)`, handlers in meta `on` (or `interceptor.on(event, handler)`, stored as `~on`), and `ctx.emit()` on every phase and action context (`withEmit`, rebound when `next()` overrides the context) runs the handlers of the interceptors applying to `ctx.command` sequentially in order; `program.emit()` uses the root with `caller: 'run'`. Signal handling is implemented as a start-phase interceptor (`padroneSignalHandling`, options `forceExitMs`/`onForceExit`, also via `builtins: { signal }`) that creates an AbortController and propagates it via `next({ signal })`; force exit is keyed on a received process signal (not on the run being aborted), and `releaseProcessSignals(ctx.signal)` (called by the repl extension for `--repl`/`repl`) unsubscribes a run from process signals so Ctrl+C belongs to the command inside the REPL. Error help display (routing/validation errors in CLI mode: the error plus a `--help` hint on stderr, or the full help with `builtins: { help: { showHelpOnError: true } }`) is handled by the help extension's error phase, not hardcoded in exec.ts; the suggestions extension's error phase adds "Did you mean" to routing errors from later phases (e.g. `help <unknown>`). Every other error in CLI mode, from any phase, is printed by auto-output's error phase (as `{ error }` JSON on stdout when `runtime.format` is `'json'`, which help's error phase defers to; `toErrorJson` strips the error's trailing `suggestions` text from `message`); extensions that print an error themselves call `markErrorReported(error)` (`src/extension/utils.ts`) so it isn't printed twice. A caller's `signal` (`eval`/`cli`/`run` preferences) becomes the base signal, which the signal extension follows; serve passes the request's signal, `tool()` the AI SDK's `abortSignal`, and MCP aborts a call on `notifications/cancelled` (request ids are scoped per HTTP session). Dynamic shell completion: `padroneCompletion()` answers `<program> __complete2 <words>` from a start-phase interceptor using `getCompletionResult` (`src/feature/complete.ts`): `value\tdescription` lines, then a directive line (`:files`, `:dirs`, `:ext:json,yaml`, `:commands`, `:nofiles`, from field `hint` via `hintDirective`) for the scripts' fallback; `__complete` (values only) stays for older scripts and the docs terminal. `generateCompletion` emits scripts that call it when that interceptor is registered; the static scripts share the per-shell fallbacks and quote enum values per shell. Both offer option names as help shows them (`offeredLongNames`: kebab-case in place of camelCase), short flags for `-`/`-x`, and never hidden commands/options; deprecated ones only complete when nothing else matches the typed prefix (static scripts leave them out). A `""` last word counts as empty (the PowerShell script passes it, as Windows PowerShell 5.1 drops empty arguments), and bash scripts read candidates with `bashReadLines` so they aren't glob-expanded. `completion --instructions` prints install instructions for the named or detected shell. `help --search <term>` uses `searchHelp` (`src/output/help-search.ts`). Man pages from `generateDocs` escape lines that would start with `.` (`manJoin`), put the date (`date` option, `SOURCE_DATE_EPOCH`, or today) and `<program> <version>` in `.TH` and link parent/subcommand pages under SEE ALSO. `repl({ historyFile, historySize })` persists history (`openHistoryFile` in `src/feature/repl-loop.ts`; `true` means `repl_history` in `program.dirs.state`; written with mode `0600`, `historySize: 0` keeps none); a mistyped `.scope` gets suggestions, and in a scope `help <cmd>` becomes `help <scope> <cmd>`. Field `valueName` replaces placeholders in help/docs (`positionalLabel`/`optionPlaceholder` in `src/output/formatter.ts`). Deprecation warnings for deprecated commands/options are printed from the parse phase for `cli` and `repl` callers. Help customization: `.configure({ help })` takes `{ usage, before, after }` (copied into `HelpInfo` by `getHelpInfo`, rendered by every formatter) or a function applied in `generateHelp` (nearest from the command up). `padroneHelp({ pager })` pages help taller than `runtime.terminal.rows` in `cli()` through `src/feature/pager.ts` (a paged help returns no result, so auto-output doesn't print it again). Help/version flag names come from `padroneHelp({ flags })`/`padroneVersion({ flags })`; they are stored as `flagNames` on the built-in command so help hints and shell completion can find them. `padroneHelp({ topics })` is stored as `helpTopics` on the help command; `getHelpTopics(root)` (`src/output/help.ts`, leaving out names a command shadows) feeds `help <topic>`, the "Additional help topics" section (`HelpInfo.topics`), suggestions for `help <typo>`, `help <word>` completion, and `topics/<name>.md` in Markdown docs.

**Extension system**: Build-time composition via `.extend(extension)`. A `PadroneExtension` is a function that receives the builder and returns a modified builder, enabling reusable command/config bundles. Unlike interceptors (which hook into runtime phases), extensions operate at definition time to compose commands, arguments, and configuration. Built-in extensions are included by default via `createPadrone()`: help (-1001.5), version (-1000), repl (-1000), color (-1001), suggestions (-500), signal (-2000), autoOutput (-1100), stdin (-1001), interactive (-999). Numbers are interceptor `order` values (lower = outermost). User-facing builtins (help, version, repl) can be individually disabled via `{ builtins: { help: false } }`. Advanced opt-in extensions imported from `'padrone'`: logger (stderr by default, colored by `runtime.terminal.stderrIsTTY`; `redact` paths (class instances too, errors left alone), `destination`, `child()` bindings), timing (`format`, `Failed after`), progress (`isActive`/`isPaused`; redraws count rows per line by `displayWidth`; `progress.tasks()` task lists in `progress-tasks.ts` with `retry`/`rollback`, `rendererOptions`, and `createSimpleTaskList` as the non-TTY fallback), update-check (`createUpdateChecker` in `feature/update-check.ts` notifies from the cache (`isVersion` drops registry/cache values that aren't versions; a future `lastCheck` is stale), `update-check.json` in `program.dirs.cache`, and refreshes a stale one with `refreshCacheFile`, stringified into a detached `-e` process by `refreshInBackground` so exit never waits; `{ notify, refresh }` lets tests await it), env, config (file loading, `merge` and `extends` in `config-loader.ts`, where a data config or `package.json` key can't extend a script config; `--config` (listed in help via `meta.helpOptions`) and `--profile` (unless `profiles: { remote: true }`) are ignored for remote callers, so they stay unknown options; `profiles` via `applyProfile`, then `sections: true` via `applySections` (a key naming a subcommand is that command's section, never a value); `command: true` adds the `config get|set|unset|list|path|edit` group in `config-command.ts` (`--local` via `findLocalConfigFile`, `--file`; `set`/`unset` edit JSONC in place through `src/util/jsonc.ts`, falling back to rewriting JSON), which disables the config interceptor for itself), json (`--json`; `--jq`/`--template` use the jq subset in `src/util/jq.ts` (parser; values, operators, builtins and `@formats` in `src/util/jq-builtins.ts`; `as $x` bindings are parse-time slots set while their body runs; `from_entries` follows jq 1.7.1, strings compare by code point, constructed objects keep `__proto__` keys) and hand auto-output a filter via `setJsonOutputFilter`; `--jq` prints compact JSON unless `runtime.terminal.isTTY`; `fields` selects keys), format (`-o <format>`: json sets `runtime.format`, yaml/csv/tsv/table hand auto-output an `OutputRenderer` via `setOutputRenderer`, which JSON output overrides; `columns` gives default columns and header labels, `pipedTable: 'tsv'` renders table as tsv off a TTY, `csvLineEnding: 'crlf'` appends `\r` to each line; YAML emitter in `src/util/yaml.ts`), confirm (`mutation: true` commands, `--yes`, or the `env` variable, `<PROGRAM>_YES` by default via `programEnvVar`), upgrade (`upgrade` self-update; `fetchLatestVersion`/`isNewerVersion` in `feature/update-check.ts`; its command interceptor, order -999, asks the registry before `padroneConfirm()` (-998) prompts, returns the `--check`/up-to-date message itself and sets the result's `exitCode` for `--exit-code` in shutdown; a root marker interceptor gives `getUpgradeConfig(root)` to update-check and `version --check` (`checkForUpdate` in `extension/update-check.ts`); `getVersion()` in `src/util/utils.ts` falls back to `readScriptVersion()`, the nearest named `package.json` above `process.argv[1]`, never the working directory), aliases (expands the first input word in the parse phase with `$N`/`$@` placeholders; user aliases in `aliases.json` under `program.dirs.config`; an alias's own `@file` words go through `expandResponseFiles` when `responseFilesPrefix(root)` finds the response-files extension; with no alias to expand it passes the alias names to suggestions as `next({ [aliasNamesKey]: names })`; `alias set <name> …` gets a `--` inserted after the name so the rest is kept literally), response-files (expands `@file` tokens in the parse phase, order -1600, before aliases; a token that would be the value of a `fromFile` option on the routed command, found by `isFromFileValue` via `parseCommand`, is left to `fromFile`). Suggestions leave out empty names (`suggestSimilar`), and unknown options are also matched against long `meta.options` names of the chain's interceptors (not help's extra options, nor version's on subcommands). `program.dirs` comes from `getProgramDirs` (`src/util/dirs.ts`); `runtime.editor`/`open`/`page` default to `src/feature/system.ts` (the editor's temp path is `shellQuote`d, `src/util/shell-utils.ts`, as are `padrone link` shims; `systemOpenCommand` builds the escaped Windows `cmd /c start` line) and `pageWithRuntime` (`src/feature/pager.ts`), and `page`/`editor` defaults use `this` (the runtime they're called on). `meta.requires` (or `.requires<T>(...ids)`) is checked by `checkInterceptorRequirements` in `exec.ts`/`run()`. Help's `pickSubcommand` and suggestions' `run: 'prompt'` re-run the parse phase with a corrected input via `next({ input })`. Arguments meta `exactlyOne`/`atLeastOne` (one group or an array of groups, also on `.globalArgs()`) become groups in `extractFieldRules`. Optional integrations with heavier transitive surfaces live in their own subpath entry points so the main bundle stays lean: `padrone/ink`, `padrone/mcp`, `padrone/serve`, `padrone/tracing`, `padrone/completion`, `padrone/man`. Color detection is `shouldUseAnsi(env, isTTY)` (`src/output/styling.ts`), checked in order: `FORCE_COLOR`, `NO_COLOR`, `CLICOLOR_FORCE`, `CLICOLOR=0`, `TERM=dumb`, `isCI`, the TTY; `--color=<theme>` must name one of `colorThemes`.

**Schema-aware parsing**: Tokenization follows routing and each option's schema type. `parseCliInputToParts(input, resolver)` (`src/core/parse.ts`) asks a `ParseResolver` (built by `createParseResolver` in `src/core/validate.ts`) for each option's `OptionArity`: `flag` (booleans; never take the next token unless it's a boolean word), `value` (always take a value, even one starting with `-`), `optional` (boolean|value unions; take the next token only if it doesn't look like an option or subcommand), `array` (like `value`, plus `[a,b]` syntax), `count` (`count: true` meta; never takes a value), `variadic` (`variadic: true` on arrays; takes tokens up to the next option or `--`), `json` (objects, records and arrays of objects; like `value`, and an attached `[...]` isn't split). `parseCommand` parses a JSON value for `json` options (`parseJsonArg` in `args.ts`; invalid JSON is a parse issue), merges it with dotted keys (`mergeObjects`, later wins) and accumulates arrays of objects; `coerceArgs` also parses JSON strings for them (env values, `fromFile` text). `serializeArgsToFlags` emits dotted keys for flat objects and JSON when they can't express the value (`isDottable`: keys with dots, arrays inside, empty objects); `stringify()` quotes tokens with `quoteToken`. Lookup order: the current command's schema, then `meta.options` declared by interceptors on the command chain (how built-ins like help/config/logger declare `--help`, `-c`, `--log-level`). Similarly, `meta.env` (`{ arg: 'VAR' }` or `(arg) => 'VAR'`, set by `padroneEnv({ vars, prefix })`) tells help which env variables feed each option. Only root interceptors run the start/parse phases, so extensions that read their flags in parse (logger, timing, json) also read them in validate when applied to a command. Extensions that touch the terminal or process stdin (stdin, progress, timing) skip remote callers (`serve`, `mcp`, `tool`; stdin with `callers: LOCAL_CALLERS`, the others with `isRemoteCaller` in `src/extension/utils.ts` where only part of the interceptor is skipped), and auto-output collects their streamed results without printing. Serve and MCP pass args to `eval()` as argv tokens (`serializeArgsToFlags(args, command)` in `src/core/commands.ts`), never a joined string. Config and env values go through `valuesForCommand` (`src/extension/utils.ts`: option names, aliases and kebab-case keys only, `null` as unset, positionals typed on the command line win) before `applyValues`, which fills nested objects key by key. Neither fills built-in commands (`builtin: true` from `.configure()`, set by the help/version/repl/completion/man/serve/mcp/config/alias/upgrade extensions; `isBuiltinCommand` in `src/core/commands.ts` checks ancestors too) unless their `builtins: true`; env's help `meta.env` function gets the command for the same reason. Both annotate validation issues about values they filled with their source (`withIssueSources`/`addedPaths` in `src/extension/utils.ts`: `(from APP_PORT)`, `(from config.json)`; `sourceOf` gets the issue's own path, so nested values name the right layer). Env: `prefix` also reads `PREFIX_DB__HOST` as `db.host`, dotted `vars` keys set nested values, empty variables are unset unless `allowEmpty`. Dotenv (`src/util/dotenv.ts`): an unclosed quote reads as unquoted, whitespace before `#` starts a comment, `Object.prototype` names never expand. `coerceArgs` also turns a number or boolean into the option's scalar type (via its string form), so YAML `name: 123` fits a string. Interceptor `meta.async: true` (config, env with files) makes `isAsyncCommand` true for the commands it applies to. Boolean framework flags are read with `frameworkFlags().flag()`/`toFlag()` so `--yes=false` is off. `fromFile` field meta: `readFileValues` (`src/core/from-file.ts`, called in `execCommand` before the validate chain, so env/config values are never read) replaces `@path`/`-`/`@@x` command-line values in place for non-remote callers; failures join `parseIssues`. `meta.stdin` is a field name or `{ field, trim }` (read with `getStdinConfig` in `src/core/args.ts`; `resolveStdin` treats any stdin with `isTTY: true` as absent, and `fromFile`'s `-` only conflicts with a stdin field that would read); the stdin extension also reads stdin for a lone `-` value (option or positional, replaced in place) and trims number/boolean fields. Sync file reads go through `readTextFile` (`src/util/files.ts`). Repeated non-array options keep the last value. Extra positionals are validation errors. Option paths through `__proto__`/`constructor`/`prototype` are stored flat so they can't pollute prototypes.

**Global args**: `.globalArgs(schema, meta?)` stores `globalArgsSchema`/`globalArgsMeta` on a command; `getGlobalArgs(cmd)` (`src/core/commands.ts`) returns the nearest self-or-ancestor definition (the function form extends the inherited one). Parsing merges global flags/aliases/arity under the command's own; `splitGlobalArgs` in `validate.ts` routes keys the command doesn't define itself to the global schema, validates both, and merges (`{ ...globals, ...own }`). Types: `TGlobals` is the 11th builder/program param; `WithGlobalArgs<TArgs, TGlobals>` gives the merged args type used by `action` and the command's `'~types'`. Async or interactive globals (`isAsyncCommand`/`usesInteractive` in `results.ts`) make the whole subtree async: at the type level interactive meta brands `TGlobals` with `'~async'`, and fresh subcommand builders start with `OrAsync<false, TParentGlobals>`. Interactive prompting covers the command's fields plus the global ones it doesn't override. Object fields are prompted key by key (`db.host`) by `promptAt` in `src/feature/interactive.ts`; blank answers to required fields are asked again. Nested sensitive keys get masked prompts, and under forced prompting a blank masked answer keeps the given value.

**Field rules**: `count`, `conflicts`, `implies`, `requires`, `requiredIf` and `requiredUnless` field meta are read by `extractFieldRules` (`src/core/args.ts`). Count fields get the `count` arity and accumulate in `parseCommand`; `applyFieldRules` runs in `buildCommandArgs` on user-provided values (conflicts first, then implies, before coercion and defaults); `checkFieldRequirements` runs after coercion (implied values count, `requiredIf` compares typed values), with issue paths at the missing option, which `buildCommandArgs` returns as `missing` so the interactive extension can prompt it. `sensitive: true` (`isSensitiveField`) hides a field's default/examples in help, marks it `writeOnly` in `buildInputSchema`, uses a password prompt, and `redactArgs(command, args)` (`src/extension/utils.ts`, exported) redacts it for extensions that log args. Extensions that read framework flags from `rawArgs` go through `frameworkFlags()` (`src/extension/utils.ts`), which skips keys the command defines itself.

**Flags vs aliases vs negatives**: `flags` = single-char short flags (`-v`), stackable. `alias` = multi-char alternative long names (`--dry-run`). `autoAlias` (default: true) auto-generates kebab-case aliases for camelCase option names. `negative` = custom negation keyword(s) for booleans (`negative: 'remote'` makes `--remote` set the arg to `false` and disables `--no-` prefix). Set to `''` or `[]` to only disable the prefix.

**Validate overrides**: what validate interceptors pass to `next()` (e.g. env's runtime with `.env` variables) carries into the execute context (`validatedCtx` in `execCommand`).

**Execution paths**: `eval()`/`cli()` runs all 7 interceptor phases; `parse()` runs parse + validate; `run()` runs execute only (no validation). `repl({ context })` passes the context to each command; the `repl` command and `--repl` pass on the caller's (pre-transform) context from the repl interceptor's start phase.

**Context**: User-defined, strongly-typed object that flows through the command tree. Defined via `.context<T>()` (type-only) or `.context(transform)` (with runtime callback). Subcommands inherit the parent context type but can transform it. `mount()` accepts an optional `{ context }` option for context transforms. Context is provided at invocation via `cli()`, `eval()`, `run()`. Resolved by walking the command parent chain and applying transforms from root to target. Available in action handlers via `ctx.context` and in all interceptor phase contexts.

**Mutation commands**: `.configure({ mutation: true })` marks a command as performing side effects. Affects serve (POST-only, experimental), MCP (`annotations.destructiveHint`, experimental), and tool() (`needsApproval` default). `.configure({ needsApproval })` (a boolean, or a function of the validated args: `PadroneCommandConfig<TArgs>` gets them from `configure`'s builder type) overrides that default.

**Remote callers**: `.configure({ outputSchema })` (`buildOutputSchema` in `src/core/commands.ts`) becomes the MCP tool's `outputSchema` (object schemas only) and the OpenAPI `result`; MCP also returns plain-object results as `structuredContent`. `collectEndpoints` leaves hidden and built-in commands out of serve/MCP, and `localOnlyInterceptor()` (`src/extension/utils.ts`) makes `config`, `alias`, `completion`, `man`, `serve`, `mcp` and `upgrade` refuse remote callers. MCP Streamable HTTP and serve reject a request whose `Origin` isn't loopback or the explicit `cors` origin (`isAllowedOrigin` in `src/core/commands.ts`, 403; serve also allows same-origin, its `Host`), and a non-loopback `Host` when bound to a loopback host (`isAllowedHost`); `maxBodySize` (default 4 MiB, `readBodyText` in `src/util/stream.ts`) caps request bodies with 413. MCP `DELETE` aborts the session's calls in flight. Serve responses carry `stderr` (lines from `runtime.error`) next to `output`; `createSensitiveQueryCheck` in `src/feature/serve.ts` rejects `sensitive` fields in GET query strings (and objects/arrays holding one, `containsSensitive`), which the OpenAPI GET parameters leave out. Tracing names the root span `<caller> <command>`, with `SpanKind` server for serve/MCP and internal otherwise, and sets the status message from the error.

**Dry runs**: `.dryRun(handler)` stores `command.dryRun`. The `--dry-run`/`-n` flag exists only on such commands (`getDryRunFlagKeys` in `validate.ts`, which also gives the parse resolver its arity and skips names the command's own options use), so elsewhere it's an unknown option and can't be ignored. `execCommand` takes the flag out of `rawArgs` after routing (`takeDryRunFlag`), sets `ctx.dryRun` on the execute context, and `coreExecute` calls `command.dryRun` instead of `command.action`. Types: `.dryRun<TDryRes>()` widens `TRes` to `TRes | TDryRes` (no extra builder generic), so it must come after `.action()`, which sets `TRes`. Help, completion, `parse()` (`dryRun`), `tool()` approval, and `buildInputSchema` (a `dryRun` property for MCP/serve) all follow it; `padroneConfirm()` skips the prompt.

## Coding Conventions

- Prefer colocation
- Use TypeScript with strict typing. Avoid `any` unless absolutely necessary.
- When importing internal modules, use absolute imports starting with `#src/`. Also include file extensions (e.g., `import { env } from '#src/env.ts'`).
- Always use top-level `import type` for type imports. Never use inline `import('./module.ts').Type` syntax in type annotations.
- Avoid verbose code comments; write self-explanatory code. Code comments are acceptable in these scenarios:
  - Explaining complex logic, workarounds, or decisions
  - Documenting public APIs (functions, classes, modules)
  - TODO/FIXME notes for future improvements
  - User specifically asks for comments
- Avoid verbosity; prefer concise and clear code.
  - Prefer early returns to reduce nesting.
  - Prefer single line if statements for simple conditions.
- If a file length becomes too long (e.g., >600 lines), consider refactoring into smaller modules.
- Check for existing utilities/hooks/components before creating new ones. Avoid code duplication.
